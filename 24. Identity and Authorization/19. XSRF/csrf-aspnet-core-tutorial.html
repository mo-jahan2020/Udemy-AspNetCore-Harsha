🔐 آموزش محافظت در برابر حملات CSRF در ASP.NET Core

پاسخ چهار سؤال کلیدی دربارهٔ AntiForgery در سطح Program.cs، کنترلر، اکشن و View.

سؤال ۱: آیا فیلتر سراسری در Program.cs کافی است؟

بله، به شرطی که فرم‌هایتان استاندارد باشند. فیلتر سراسری فقط «اعتبارسنجی» را سراسری می‌کند؛ «تولید توکن» در سمت View اتفاق می‌افتد که فرم‌های استاندارد آن را خودکار انجام می‌دهند.

سمتوظیفهکجا انجام می‌شود؟
تولید توکنتوکن ساخته و داخل فرم قرار می‌گیردView
اعتبارسنجی توکنسرور معتبر بودن توکن را بررسی می‌کندController (با فیلتر سراسری)

تنظیم سراسری در Program.cs:

builder.Services.AddControllersWithViews(options =>
{
    options.Filters.Add(new AutoValidateAntiforgeryTokenAttribute());
});

سؤال ۲: باید روی همهٔ کنترلرها [AutoValidateAntiforgeryToken] بنویسم؟

خیر این دقیقاً همان کاری است که فیلتر سراسری می‌کند؛ نوشتن دوبارهٔ آن روی تک‌تک کنترلرها تکرار بیهوده است.

// ❌ لازم نیست — فیلتر سراسری همین را برای همه انجام می‌دهد
[AutoValidateAntiforgeryToken]
public class AccountController : Controller { ... }

فقط در دو حالت این ویژگی را می‌نویسید:

  • وقتی فیلتر سراسری ندارید ولی می‌خواهید فقط یک کنترلر خاص محافظت شود.
  • وقتی می‌خواهید روی یک کنترلر حساس (مثلاً پرداخت) صراحتاً برچسب امنیتی بگذارید.

سؤال ۳: باید روی همهٔ اکشن‌های POST بنویسم [ValidateAntiForgeryToken]؟

خیر با وجود فیلتر سراسری، همهٔ متدهای ناامن (POST، PUT، PATCH، DELETE) به‌صورت خودکار بررسی می‌شوند. تنها چیزی که ممکن است بنویسید، استثنا کردن موارد خاص است:

[HttpPost]
[IgnoreAntiforgeryToken] // ⚠️ فقط برای موارد خاص مثل Webhook خارجی
[Route("api/payment-callback")]
public IActionResult Callback(...) { ... }

تفاوت ظریف برای یادگیری عمیق‌تر:

  • [ValidateAntiForgeryToken] روی هر متدی که بگذارید، حتی GET هم توکن می‌خواهد.
  • [AutoValidateAntiforgeryToken] فقط متدهای ناامن را بررسی می‌کند و GET آزاد می‌ماند.

سؤال ۴: روی View های POST چه چیزی بنویسم؟

هیچ چیزی! به شرطی که یکی از این سه الگوی استاندارد را استفاده کنید:

✅ الگوی ۱ — MVC با Tag Helper (توکن خودکار اضافه می‌شود):

<form asp-action="Transfer" method="post">

✅ الگوی ۲ — Razor Pages (کاملاً خودکار):

<form method="post">

✅ الگوی ۳ — HTML Helper (خودکار):

@using (Html.BeginForm("Transfer", "Account", FormMethod.Post))
{
    ...
}

⚠️ تنها حالت خطرناک فرم دستی با action دست‌نویس است که توکن به آن اضافه نمی‌شود:

<!-- ⚠️ این حالت توکن ندارد -->
<form method="post" action="/Home/Transfer">
    <input name="__RequestVerificationToken"
           type="hidden" value="..." /> <!-- باید دستی اضافه شود -->
</form>

راه‌حل: به فرم asp-antiforgery="true" اضافه کنید یا داخل فرم بنویسید @Html.AntiForgeryToken()

📋 خلاصهٔ نهایی

  • بله فیلتر سراسری در Program.cs کافی است + فرم‌های استاندارد خودشان توکن می‌سازند
  • نه نیازی به ویژگی روی همهٔ کنترلرها نیست؛ فیلتر سراسری جایگزین آن است
  • نه نیازی به ویژگی روی همهٔ اکشن‌های POST نیست؛ فقط Ignore برای استثناها
  • نه در View ها چیزی لازم نیست؛ فقط از Tag Helper فرم استفاده کنید

مکانیزم کار (Double-Submit Cookie): توکن همزمان در یک کوکی به نام AspNetCore.Antiforgery.xxx و در یک فیلد مخفی فرم قرار می‌گیرد؛ سرور تطابق این دو را هنگام Submit بررسی می‌کند.

🧪 تمرین عملی (برای یادگیری عمیق)

  • گام ۱: یک فرم POST بسازید و Submit کنید → باید درست کار کند ✅
  • گام ۲: در DevTools مرورگر، فیلد مخفی __RequestVerificationToken را حذف کنید و دوباره Submit کنید → خطای HTTP 400 می‌بینید ❌
  • گام ۳: کوکی AspNetCore.Antiforgery.xxx را پاک کنید و Submit کنید → باز هم 400 ❌

این تمرین نشان می‌دهد مکانیزم Double-Submit (تطابق کوکی و فیلد فرم) چگونه عمل می‌کند.

نکتهٔ جانبی: برای فرم‌های AJAX / SPA به تنظیم HeaderName و کد جاوااسکریپت نیاز دارید؛ فیلد مخفی وجود ندارد و توکن باید در هدر ارسال شود.
